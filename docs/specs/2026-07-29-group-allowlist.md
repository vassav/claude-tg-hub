# Мультипользовательский доступ: allowlist для групповых чатов

**Статус:** дизайн утверждён 2026-07-29.

## Задача

Сегодня боту может писать только владелец (`HUB_OWNER_ID`). Нужно: **добавить к текущему
поведению** обработку сообщений в групповых чатах от людей, внесённых владельцем в список.
Сессии общие (один «кабинет»), права у всех в списке одинаковые. Всё остальное поведение —
в первую очередь то, куда бот шлёт свой системный вывод — **не меняется**.

## Проверенные факты

- **Бот-админ в группе получает все сообщения.** core.telegram.org/bots/features#privacy-mode:
  «Privacy mode is enabled by default for all bots, **except bots that were added to a group
  as admins** (bot admins always receive all messages)». Значит `/setprivacy` в BotFather
  настраивать не нужно — достаточно сделать бота админом. Это условие **на каждую группу**:
  там, где он не админ, до него дойдут только команды, реплаи на его сообщения и упоминания.
- **Bot API не умеет `@username → user_id`.** Id человека узнаётся только из сообщения,
  которое он написал в чат с ботом. Основной путь добавления — реплай на его сообщение.
- **Ответы сессий уже роутятся по чату-источнику.** `t:'reply'` шлёт в `m.chat_id || CHAT`
  ([hub.mjs:593](../../tg-hub/hub.mjs#L593)), а `chat_id` приезжает из `meta` исходного
  сообщения, который собирает `routeTo` ([hub.mjs:359-363](../../tg-hub/hub.mjs#L359-L363)).
  Спросили из группы — ответ в группу. Это работает сегодня, переделывать нечего.
- **`HUB_CHAT_ID` не годится как «группа-вход».** Переменная делает две работы сразу: задаёт
  и принимаемый чат ([hub.mjs:681](../../tg-hub/hub.mjs#L681)), и адресата всего системного
  вывода — `notify` ([:204](../../tg-hub/hub.mjs#L204)), карточек аппрува
  ([:599](../../tg-hub/hub.mjs#L599), [:606](../../tg-hub/hub.mjs#L606)). Проверено живьём
  2026-07-29: с `HUB_CHAT_ID=<группа>` хаб стартует как `home chat=… (group)` и весь вывод
  уезжает в группу. Это не то, что нужно, поэтому право писать определяется не этой
  переменной, а списком плюс типом чата (§2) — новых переменных окружения не появляется.
- **Тип чата виден по знаку id.** У групп и супергрупп `chat_id` отрицательный, у личек —
  положительный (равен `user_id`). Дополнительно в апдейте есть `chat.type`
  (`private`/`group`/`supergroup`); в гейте используется он, знак id — для веток, где на
  руках только число (§4а).

## Решения (зафиксированы в диалоге)

| Развилка | Выбор |
|---|---|
| Общие сессии или изоляция по пользователям | **Общие** — группа как единый кабинет |
| Где живёт список | **`access.json` + команды владельца**, горячо, без рестарта демона |
| Права не-владельца | **Плоско: в списке = может всё** |
| На что реагирует бот в группе | **На всё**, как в личке (бот админ ⇒ видит всё) |
| Какие группы | **Любые**, где есть и бот, и человек из списка — без привязки к конкретному id |
| Личка с ботом | **Только владельцу**; из списка пишут только в группах |
| Системный вывод (`notify`, аппрувы) | **Не трогаем** — остаётся в личке владельца |
| Карточки AskUserQuestion | **В чат, откуда пришёл запрос** |

Рестарт демона как способ менять список отвергнут: он роняет живые сессии в ⏸ resume, а
список правится чаще, чем хочется терять сессии. (Реконнект проверен: shim, interposer и
headless переподключаются каждые 2 с — [shim.mjs:49](../../tg-hub/shim.mjs#L49),
[interposer.mjs:95](../../tg-hub/panel/interposer.mjs#L95),
[headless.mjs:50](../../tg-hub/panel/headless.mjs#L50) — но это про переживание рестарта,
а не про удобство.)

## 1. Модуль доступа — `tg-hub/access.mjs`

Файл `~/.claude/channels/hub/access.json`, рядом с существующим `registry.json`:

```json
{
  "version": 1,
  "users": {
    "300447655": { "name": "vassav", "role": "owner", "added": "2026-07-29T10:20:00.000Z", "by": "300447655" }
  }
}
```

Экспорт: `roleOf(id) → 'owner' | null`, `add(id, name, by) → boolean`, `remove(id) → boolean`,
`list() → [{id, name, role, added, by}]`, `reload()`, плюс чистый предикат гейта
`canUse({ userId, chatType, isBot }, { owner }) → boolean` (см. §2). Внутри — `Map`,
читается один раз при старте, пишется на каждое изменение.

- **Запись атомарная**, по образцу `saveRegistry()` ([hub.mjs:130-139](../../tg-hub/hub.mjs#L130-L139)):
  `openSync(tmp,'w')` → `writeSync` → `fsyncSync` → `closeSync` → `renameSync`. Директория
  создаётся через `mkdirSync(..., {recursive:true})` перед записью (self-heal).
- **Чтение отказоустойчивое**, по образцу `loadRegistry()` ([hub.mjs:142-148](../../tg-hub/hub.mjs#L142-L148)):
  `ENOENT` → пустой список (норма, не ошибка); битый JSON → файл переименовывается в
  `access.json.corrupt-<ts>`, работаем с пустым списком и пишем в лог. Пустой список ⇒
  доступ только у владельца — деградация в безопасную сторону.
- `role` пишется всегда `"owner"` (плоская модель прав) и читается через `roleOf`. Поле
  зарезервировано под будущую роль `writer` — добавляется без миграции формата.
- Секций `groups` и `pending` (в отличие от плагина) нет: группы не перечисляются (§2),
  pairing-кнопки не делаем (§6).

Модуль не знает про Telegram и grammy — чистые функции над файлом, тестируются напрямую.

## 2. Гейт доступа

Новых переменных окружения нет. Право писать = членство в списке + тип чата.

```js
// access.mjs
export function canUse({ userId, chatType, isBot }, { owner }) {
  if (isBot) return false;
  if (String(userId) === String(owner)) return true;          // владелец — где угодно
  return chatType !== 'private' && !!roleOf(String(userId));  // из списка — в любой группе
}

// hub.mjs
const owns = ctx => access.canUse(
  { userId: ctx.from?.id, chatType: ctx.chat?.type, isBot: ctx.from?.is_bot },
  { owner: OWNER });
```

Таблица решений:

| Кто | Где | Итог |
|---|---|---|
| владелец (`HUB_OWNER_ID`) | личка | ✅ (как сегодня) |
| владелец | любая группа | ✅ (как сегодня) |
| человек из `access.json` | любая группа, где есть бот | ✅ **(новое — вся суть правки)** |
| человек из `access.json` | личка с ботом | ❌ |
| человек не из списка | где угодно | ❌ (молча, как сегодня) |
| другой бот | где угодно | ❌ (`is_bot`) |

Существующая клауза `String(ctx.chat?.id) === CHAT` из
[hub.mjs:681](../../tg-hub/hub.mjs#L681) **снимается**: она пускала в домашний чат кого
угодно. Пока `HUB_CHAT_ID` не задан (текущее состояние `.env`), это ничего не меняет —
`CHAT === OWNER`, и клауза дублировала проверку на владельца. Если `HUB_CHAT_ID` когда-нибудь
зададут группой, доступ там будет определяться списком, а не фактом членства в чате.

Пустой `access.json` ⇒ вторая ветка никогда не срабатывает ⇒ поведение ровно как сегодня.
Отказ молчаливый (`return` без ответа) — бот в группе не должен огрызаться на каждое чужое
сообщение.

**Принятая цена «любой группы».** Человек из списка может позвать бота в свою группу и
работать там; посторонние в той группе управлять ботом не смогут (их нет в списке), но
**увидят ответы**, а в них — код и содержимое проектов. Список короткий и состоит из
доверенных людей, поэтому вариант со списком разрешённых групп (секция `groups`, как у
плагина) сознательно не делается. Системного вывода и аппрувов это не касается — они
адресованы в `CHAT`, то есть в личку владельца (§5).

## 3. Команды

| Команда | Кто может | Поведение |
|---|---|---|
| `/allow` реплаем на сообщение человека | владелец | берёт `reply_to_message.from` (`id`, `username`/`first_name`), добавляет, отвечает «✅ Иван (123456789) добавлен» |
| `/allow <id> [имя]` | владелец | то же по явному id; без аргументов и без реплая — подсказка по формату |
| `/deny` реплаем, либо `/deny <id>` | владелец | удаляет; если не было в списке — «его и не было» |
| `/who` | любой из списка | список: имя, id, кто добавил, когда; владелец помечен отдельно |
| `/id` | **любой в групповом чате**; в личке — только владелец | отдаёт `chat_id`, `type`, собственный `user_id` |

Управление списком (`/allow`, `/deny`) — **только владелец из env**, даже при плоской модели
прав: иначе список расширяет сам себя и перестаёт быть списком. Попытка не-владельца →
«только владелец может менять список».

`/id` ([hub.mjs:686](../../tg-hub/hub.mjs#L686)) сейчас закрыт `owns()` — открывается для
групповых чатов: он отдаёт человеку только его собственный id и id чата, секретов не несёт.
Основной путь добавления от него не зависит: бот-админ видит сообщение новичка (даже когда
хаб его игнорирует), владелец отвечает на это сообщение `/allow`.

Добавление вступает в силу мгновенно — следующее сообщение человека уже проходит гейт.

## 4. `lastInbound`: атрибуция ответов и адрес ask-карточек

Одна структура на два применения. Хаб держит `lastInbound: sessionId → { chat_id, message_id, user }`,
проставляемую в `routeTo()` ([hub.mjs:359-366](../../tg-hub/hub.mjs#L359-L366)) — там уже
собирается ровно этот `meta`. Сессия обрабатывает один ход за раз, поэтому «последний, кто
написал в эту сессию» и есть тот, кого касается происходящее.

**(а) Атрибуция ответов.** Когда в группе пишут двое, два ответа подряд без адресата
неразличимы. Ветка `t:'reply'` ([hub.mjs:593](../../tg-hub/hub.mjs#L593)) отправляет ответ с
`reply_to_message_id` из `lastInbound` — при условии, что чат групповой и это тот же чат,
куда уходит ответ (`lastInbound.chat_id === chat_id`). Групповой чат определяется по знаку
id: у групп и супергрупп он отрицательный, у личек положительный. В личке — без реплая,
как сейчас.

Технически это `reply_parameters: { message_id, allow_sending_without_reply: true }`
(Bot API 7.0+, поддержан grammY 1.30), а не устаревший `reply_to_message_id`: флаг
`allow_sending_without_reply` заставляет Telegram отправить сообщение обычным, если
процитированное удалили, — отдельная ступень фолбэка в `sendTg` не нужна. В `sendTg`
([hub.mjs:258-270](../../tg-hub/hub.mjs#L258-L270)) появляется пятый аргумент `firstExtra`:
`extra` кладётся на последний кусок (там клавиатура), а цитата должна висеть на первом.

**(б) Адрес ask-карточек.** Карточка AskUserQuestion уходит в чат-источник, а не в домашний.
`askState` при создании запоминает `chatId` (из `lastInbound` этой сессии, иначе `CHAT`), и
все пять точек работы с карточкой берут адрес оттуда вместо жёсткого `CHAT`:
отправка [hub.mjs:599](../../tg-hub/hub.mjs#L599), отмена
[:811](../../tg-hub/hub.mjs#L811), перерисовка при мультивыборе
[:833](../../tg-hub/hub.mjs#L833), переход к следующему вопросу
[:841](../../tg-hub/hub.mjs#L841), финальное summary [:846](../../tg-hub/hub.mjs#L846).

Имя автора модель уже видит: `routeTo` кладёт `user`/`user_id` в `meta`, они доезжают до
движка тегом `<channel … user="…">`. Ничего добавлять не нужно.

## 5. Аппрувы инструментов — без изменений

Карточка `🔐 <tool>` с ✅/❌ и `notify` по-прежнему уходят в `CHAT`
([hub.mjs:204](../../tg-hub/hub.mjs#L204), [:606](../../tg-hub/hub.mjs#L606)), то есть в
личку владельца. Кнопки проходят через тот же `owns()`
([hub.mjs:741](../../tg-hub/hub.mjs#L741)).

Отсюда важное свойство: участник группы **физически не может** нажать ✅ на
`Bash(rm -rf …)` — карточка в группе не появляется. Не потому что проверяются права, а
потому что кнопки перед ним нет. Плоская модель прав (все в списке равны) становится
безопасной без ролей.

Обратная сторона, принимается сознательно: пока владелец не подтвердит аппрув в личке,
автор задачи в группе видит тишину. Уведомление «⏳ жду подтверждения владельца» в группу
не шлём (§6).

## 6. Вне объёма

Отдельные сессии на пользователя; роли `writer`/`owner`; pairing-кнопки «впустить
незнакомца» с секцией `pending`; уведомление в группу о том, что задача ждёт аппрува;
форум-топики (`message_thread_id`); несколько групп; `HUB_ALLOW_IDS` в env как второй
источник правды. Всё перечисленное надстраивается поверх этого дизайна без его переделки.

## 7. Проверка

`tg-hub/access-test.mjs` — по образцу существующих `smoke-*.mjs`, без сети и без Telegram,
`HOME`/`USERPROFILE` подменяется на временную директорию:

1. пустой старт (файла нет) → `roleOf` любого → `null`, ошибок нет;
2. `add` → `roleOf` → `'owner'`; `list()` содержит имя и `by`;
3. персист: `reload()` видит запись;
4. `remove` → `roleOf` → `null`, файл обновлён;
5. битый JSON → бэкап `.corrupt-*` создан, список пустой, исключения нет;
6. таблица гейта из §2 на `canUse`: owner/личка, owner/группа, списочник/группа,
   списочник/супергруппа, списочник/личка, чужак/группа, бот/группа, плюс пустой список →
   не проходит никто, кроме владельца.

Живая проверка (бот добавлен в группу админом, рестарт хаба не нужен — список читается
горячо; `.env` не меняется):

- второй аккаунт пишет в группу до `/allow` → молчание; в личке боту → молчание;
- владелец делает реплай `/allow` → «добавлен»; тот же человек пишет снова → ответ приходит
  **в группу, реплаем на его сообщение**;
- задача из группы упирается в аппрув → карточка `🔐` приходит **владельцу в личку**, в
  группе её нет;
- модель задаёт AskUserQuestion по задаче из группы → карточка с кнопками **в группе**;
- `/deny` → снова молчание.
