# Rich Messages: нативный рендер ответов и пузырь `<tg-thinking>`

**Статус:** дизайн утверждён 2026-07-29, механизм проверен на живом Bot API.

## Задача

Ответы сессий уходят в Telegram через `mdToTgHtml` — регулярки, превращающие Markdown в
подмножество HTML, которое понимает `sendMessage`. Таблиц в этом подмножестве нет, поэтому
`| PR | Тема | Δ |` прилетает пайпами и разъезжается по ширине экрана. Bot API 10.1 умеет
**Rich Messages** — сообщение как документ, с настоящими таблицами, заголовками, списками и
подсвеченным кодом. Нужно: отдавать ответы через них, а на время работы сессии показывать
живой индикатор вместо тишины.

## Проверенные факты

Всё ниже проверено 2026-07-29 живыми запросами нашим ботом. Зонды с несуществующим
`chat_id: 1` ничего не отправляли: валидация тела идёт раньше проверки чата, поэтому
«chat not found» = тело принято.

**Методы существуют.** `sendRichMessage` и `sendRichMessageDraft` на пустом теле отвечают
`400 "rich message must be non-empty"`, контрольный несуществующий метод — `404 Not Found`.

**Три режима содержимого:** `markdown`, `html`, `blocks` (поля `InputRichMessage`).

**Режим `markdown` — то, что нам нужно.** Одного поля `markdown` достаточно, `text` не
требуется. Проверено рендером: `## заголовок`, `**жирный**`, `` `код` ``, `[ссылка](url)`,
таблица с выравниванием `|--:|`, маркированный список, ```` ```js ```` и `> цитата` —
всё отрисовано нативно, таблица с границами, зеброй, выравниванием чисел вправо и переносом
внутри ячейки; блок кода — с меткой языка и подсветкой синтаксиса.

**Режим `blocks` — тупик, не используем.** Требует одновременно `text` и `blocks`;
дискриминатор — `type`; валидны `paragraph`, `table`, `heading` (`size` — число), `list`,
`divider`, `details`, `thinking`, `footer`; **не существуют** `code`, `preformatted`, `quote`,
`block_quotation`, `section_heading`, `header`. Таблица там — двумерный массив `cells`, а не
`rows[].cells[]`. Главное: **`parse_mode` и `entities` внутри блоков принимаются, но не
рендерятся** — жирный, моноширинный и ссылки приходят голым текстом (проверено обоими
способами). Набор из восьми разнотипных блоков отвергается с `RICH_MESSAGE_CONTENT_REQUIRED`,
причём удаление любого одного не помогает. Разбираться не нужно: `markdown` закрывает задачу
целиком.

**Лимиты** (из раздела «Rich Message Limits»): 32768 UTF-8 символов, 500 блоков (включая
вложенные, пункты списков, строки таблиц), 16 уровней вложенности, 50 медиа, 20 колонок в
таблице. Против нынешних 4096 символов у `sendMessage`.

**Драфты.** `sendRichMessageDraft(chat_id, draft_id, rich_message)` — эфемерное превью на
30 секунд, возвращает `True`, а не `Message`. Правки с одним `draft_id` анимируются. `chat_id`
в сигнатуре — **только приватный чат** (тип `Integer`, не `Integer or String`). Чтобы
результат остался в чате, в конце нужен обычный `sendRichMessage`. Тег `<tg-thinking>`
существует **только** в драфтах. Проверено: 30 обновлений за ~20 секунд клиент отрисовал
плавно, таблица дорастала строками без миганий, в конце корректно дорисовались блок кода и
цитата.

**grammY метода не знает** (стоит 1.43.0, в npm 1.45.1). Не помеха: в
[hub.mjs:961](../../tg-hub/hub.mjs#L961) уже есть прямой `fetch` к Bot API для скачивания
файлов — тем же путём уйдут и rich-сообщения, без новых зависимостей.

**`usage` в потоке есть.** Проверено по транскриптам движка в `~/.claude/projects/*/*.jsonl`:
`assistant`-сообщения несут `{"input_tokens":2,"cache_creation_input_tokens":1652,
"cache_read_input_tokens":415129,"output_tokens":1417,…}`. Важно: `output_tokens` — на **один
вызов API**, а ход с инструментами состоит из многих вызовов, поэтому для пузыря их надо
**суммировать по ходу**, а не показывать последнее значение. (Первый найденный
`panel-interposer-out.jsonl` оказался выводом мок-движка из смоук-тестов —
`"session_id":"mock-sid"`, `ECHO:привет` — и о реальном потоке не говорил ничего.)

## Решения

| Развилка | Выбор |
|---|---|
| Режим содержимого | **`markdown`** — отдаём текст модели как есть, парсер не пишем |
| Что делать с `mdToTgHtml` | остаётся **запасным** рендером, не трогаем |
| Где применяем rich | только ответы сессий (`t:'reply'`); служебные сообщения хаба — как сейчас |
| Коллизии синтаксиса (`$…$`, `==…==`, `![]()`) | **ничего не делаем**, смотрим на живых ответах |
| Индикатор работы | пузырь `<tg-thinking>` драфтом, время всегда, токены — если доступны |
| Стрим текста ответа по мере генерации | **вне объёма** (§5) |

## 1. Rich-рендер ответов

Новый модуль `tg-hub/rich.mjs`:

- `richBody({ chatId, markdown, extra })` — чистая функция, собирает тело запроса
  `{ chat_id, rich_message: { markdown }, ...extra }`. Тестируется напрямую.
- `sendRich({ apiRoot, token, chatId, markdown, extra })` → `Promise<Message | null>` —
  `POST ${apiRoot}/bot${token}/sendRichMessage`, `null` на любой неудаче (HTTP-ошибка,
  `ok:false`, исключение сети). Ничего не логирует громко: неудача — штатный путь.

В `hub.mjs` появляется `sendMd(chatId, text, sid, extra, firstExtra)`:

1. если `text.length <= 32768` — пробует `sendRich` с `extra`, куда сливаются `reply_markup`
   из `extra` и `reply_parameters` из `firstExtra` (метод принимает оба);
2. успех → регистрирует `message_id` в `outMsgToSession` (иначе сломается маршрутизация
   «реплай на сообщение бота → его сессия») и возвращает результат;
3. неуспех или текст длиннее лимита → вызывает существующий `sendTg` без изменений.

Ветка `t:'reply'` ([hub.mjs:600-604](../../tg-hub/hub.mjs#L600-L604)) начинает звать `sendMd`
вместо `sendTg`. Остальные вызовы `sendTg` не трогаются.

Нарезка на куски в rich-пути не нужна: до 32768 символов шлём одним сообщением, что убирает
разрыв таблицы между кусками — нынешний `chunkText` рвёт по строкам и разрезал бы таблицу
пополам.

## 2. Пузырь `<tg-thinking>`

Хаб знает обе границы работы сессии сам: `routeTo` ([hub.mjs:363](../../tg-hub/hub.mjs#L363))
— отправил вопрос, ветка `t:'reply'` — пришёл ответ. Интерпозер для этого не нужен.

Состояние: `thinking: Map<sessionId, { chatId, draftId, startedAt, tokens, timer }>`.

- **Старт.** В `routeTo`, только если чат приватный (положительный `chat_id`). `draftId` —
  ненулевое 32-битное число из монотонного счётчика демона, **новое на каждый ход**: правки с
  одним `draft_id` анимируются, поэтому один ход = один `draft_id`, а следующий ход той же
  сессии берёт следующий номер и не наследует анимацию предыдущего.
- **Обновление.** Таймер каждые 10 секунд (TTL драфта 30 — три попытки на промах) шлёт
  `sendRichMessageDraft` с `{ markdown: '<tg-thinking>' + thinkingText(entry) + '</tg-thinking>' }`.
  Rich Markdown допускает произвольный HTML, поэтому тег кладётся прямо в `markdown`.
- **Текст.** Чистая функция `thinkingText({ startedAt, tokens, now })` →
  `Thinking… · 1.8k tokens · 23 с`. Токенов нет → `Thinking… · 23 с`. Секунды до 99, дальше
  `1 м 40 с`. Токены: `<1000` как есть, дальше `1.8k`.
- **Стоп.** Первый `t:'reply'` от этой сессии; отправка карточки аппрува (сессия не думает, а
  ждёт человека — таймер гасится и заводится заново после решения); закрытие сокета сессии;
  `/stop`; предохранитель 10 минут.
- **Провал ничего не стоит.** Драфт не сообщение, привязок не имеет, `null` игнорируется.

Финализировать драфт отдельно не нужно: обычная отправка ответа (§1) и есть финализация.

## 3. Счётчик токенов и новый `status`

Хаб токенов не видит. Их видит интерпозер — в stream-json движка, где `usage` едет в
`assistant`-сообщениях (подтверждено, см. «Проверенные факты»).

В контракт интерпозер→хаб добавляется пятый тип сообщения (сейчас `reply`, `title`,
`permission_request`, `approval_cancel`):

```js
{ t: 'status', sessionId, tokens }   // СУММА output_tokens по текущему ходу
```

Сумму копит отправитель: интерпозер обнуляет счётчик, увидев `user`-сообщение (начало хода),
и прибавляет `message.usage.output_tokens` с каждого `assistant`-сообщения. Шлётся не чаще
раза в 2 секунды — дребезг не нужен, пузырь обновляется раз в 10. Хаб кладёт значение в запись
`thinking`. Симметрично правится `headless.mjs` — у него та же роль.

## 4. Деградация

| Ситуация | Что видит человек |
|---|---|
| личка, stream-сессия | `Thinking… · 1.8k tokens · 23 с`, затем rich-ответ |
| личка, channels-сессия (дефолт без `HUB_STREAM`) | `Thinking… · 23 с` — шим usage не видит |
| группа | пузыря нет вовсе (драфты только в личке), rich-ответ приходит |
| `TELEGRAM_API_ROOT` на своём Bot API старее 10.1 | ни пузыря, ни rich — всё как сегодня |
| текст длиннее 32768 или Telegram отверг содержимое | ответ уходит нынешним путём, нарезанным |

Ни в одном случае ответ не теряется: rich — это попытка поверх работающего пути, а не замена.

## 5. Вне объёма

Стрим текста ответа по мере генерации (потребует гнать в хаб частичные блоки и переписать
контракт глубже, чем `status`); режим `blocks`; автовстраивание медиа `![](url)`; формулы;
сноски; экранирование коллизий Markdown. Всё это надстраивается поверх, ничего не переделывая.

**Индикатор в группе — отложен, но возможен.** Драфт в группу отвергается отдельной ошибкой
`TEXTDRAFT_PEER_INVALID` (проверено), так что `<tg-thinking>` там недоступен. Зато в том же
Bot API 10.1 есть Ephemeral Messages: `receiver_user_id` у `sendMessage` показывает сообщение
только одному участнику, а `editEphemeralMessageText` его правит. Это отдельный код (другой
метод отправки, другой метод правки, своё `ephemeral_message_id` в `ReplyParameters`) и
непроверяемый без живой группы, поэтому берётся следующим заходом. Формулировка «в группе
пузыря нет» в §4 означает «пока нет», а не «нельзя».

## 6. Проверка

Юнитами (по образцу существующих `*-test.mjs`, без сети):

1. `richBody` — собирает `chat_id`/`markdown`, прокидывает `reply_parameters` и `reply_markup`,
   не теряет и не путает их.
2. `thinkingText` — с токенами и без; форматирование `1.8k`; переход секунд в минуты;
   нулевое время.
3. `sendRich` на подставном `fetch` — возвращает `Message` при `ok:true`, `null` при `ok:false`,
   `null` при брошенном исключении, `null` при HTTP 500.

Живьём:

- ответ с таблицей из личной сессии → нативная таблица; тот же ответ при принудительно
  сломанном `apiRoot` → приходит старым путём;
- длинный ответ (>4096, <32768) → одно сообщение, а не три;
- реплай на rich-ответ → попадает в свою сессию (проверка `outMsgToSession`);
- в группе ответ приходит цитатой на автора (не сломали §4а allowlist-спеки);
- пузырь появляется в личке, тикает, гаснет с приходом ответа; на карточке аппрува замирает.
