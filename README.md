# claude-tg-hub

Один Telegram-бот, управляющий **несколькими сессиями Claude Code** одновременно:
переписка с любой сессией, подтверждение инструментов (аппрувы) кнопками, история проектов
и возобновление (resume), создание/остановка и авто-именование сессий — через нативную фичу
Claude Code **channels**.

> **Статус: рабочий инструмент (beta).** Проверен end-to-end на `claude` 2.1.167, переживает
> рестарт/краш демона. Это не «продакшн для всех»: один владелец-бот, код на `.mjs` (без сборки),
> пути под Windows правятся вручную (см. [Установку](#установка)). Опирается на `channels` —
> research-preview Claude Code (нужен `claude` ≥ 2.1.80, первопартийный провайдер), контракт
> между версиями может меняться. Дизайн и проверенные в бинаре факты — в [`docs/`](docs/).

## Идея

Управлять своими сессиями Claude Code с телефона: писать в них, видеть ответы, подтверждать
действия (Bash/Write/…) — пока ты не за терминалом.

Ключевой плюс над официальным channel-плагином (telegram/discord/…): тот поллит Telegram
**в каждой сессии** (один бот = одна сессия, конфликт `getUpdates`). Здесь бот держит **один
долгоживущий демон**, а каждая сессия подключается тонким shim'ом по локальному IPC →
**один бот обслуживает много сессий**.

## Что умеет

- **Один бот ↔ много сессий**: единственный поллер Telegram, тонкие shim'ы по локальному IPC.
- **Маршрутизация**: активная сессия / `/to <label>` / reply на сообщение / тап по метке.
- **Аппрувы кнопками** — только на реальные действия (Bash/Write/…); ответы ассистента и
  служебные инструменты авто-разрешены, так что `reply`/`set_title` не дёргают пользователя.
- **История проектов и resume** любой прошлой сессии с полной историей разговора.
- **Сессии переживают рестарт/краш демона**: durable-реестр на диске (атомарная, краш-safe
  запись), живые переподцепляются сами, мёртвые предлагаются как ⏸ resume. Защита от
  двойного запуска одного разговора — по живости процесса (PID), а не только по сокету.
- **Авто-именование**: сама модель называет сессию по первому запросу (`set_title`), иначе —
  слаг запроса (фолбэк через 20с); имена с юникодом (в т.ч. кириллица).
- **Мост с панелью VSCode**: stdio-интерпозер (через `claudeProcessWrapper`) подключает сессию
  панели к тому же хабу — ответы зеркалятся в Telegram, сообщения из TG инжектятся в панель как
  user-turn'ы, аппрувы кнопками по control-протоколу. См. [VSCode-панель](#vscode-панель-мост-через-интерпозер).
- **Несколько человек в группе**: список доступа (`/allow`/`/deny`/`/who`) — люди из списка
  пишут боту в групповых чатах и сами отвечают на аппрувы и вопросы сессии. Отдельно —
  `HUB_CHAT_ID`: перевести весь вывод (ответы, аппрувы, уведомления) в группу вместо лички.
  См. [Бот в группе](#бот-в-группе).
- **Форматирование в Telegram**: ответы сессий рендерятся Markdown→HTML (жирный/код/блоки/ссылки),
  с плейн-фолбэком и разбивкой длинных сообщений.

## Архитектура

```
Telegram (1 бот) ─ getUpdates ─ HUB (демон): бот + IPC-сервер + реестр + роутинг + аппрувы
                                     ▲ локальный TCP IPC
                          channel-shim (на каждую сессию): MCP stdio ↔ движок,  TCP ↔ hub
                                     ▲ stdio  (claude --channels …)
                                  claude  (CLI-сессия)
```

- **`tg-hub/hub.mjs`** — демон: владеет ботом (grammY, единственный поллер), TCP-IPC, реестром
  сессий, маршрутизацией (команда / reply-to / клавиатура ↔ сессия), аппрув-кнопками, историей
  проектов + resume, созданием и остановкой сессий.
- **`tg-hub/shim.mjs`** — per-session channel-MCP-сервер (без зависимостей): объявляет
  `claude/channel` + `claude/channel/permission`, релеит вход / аппрувы / `reply`, сам находит
  хаб (discovery-конфиг) и присваивает себе id; останавливает свою сессию, убивая родителя-`claude`.
- **`tg-hub/session.mjs`** — запуск сессии в PTY (node-pty, с авто-подтверждением стартовых
  промптов); **`tg-hub/launch.mjs`** — поднять стартовые сессии.

## Команды бота

Имя сессии (`label`) ставится автоматически: модель называет её по первому запросу через
`set_title`, иначе — слаг запроса (фолбэк через 20с); до первого сообщения — имя папки проекта.
С дедупом и юникодом.

| Команда / действие | Что делает |
|---|---|
| `/start` | приветствие + клавиатура |
| `/sessions` | живые сессии (● активная, ⚡ работает, 🔐 ждёт аппрув, 🛑 стоп, 🔄 обновить) **и** ⏸ resumable (🗑 — забыть) |
| обычный текст | в активную сессию |
| тап по метке на клавиатуре | сделать эту сессию активной |
| `/to <label> <текст>` · reply на `[label]` | отправить в конкретную сессию, не меняя активную |
| `/projects` | история по проектам (cwd) → ▶ Resume или ➕ новая сессия |
| `/new <путь>` | создать новую сессию в указанной папке |
| `/stop <label>` (или 🛑) | остановить сессию |
| `/id` | показать `chat_id` текущего чата и свой `user_id` (в группе доступна всем) |
| `/allow` | (владелец) добавить человека в список доступа — реплаем на его сообщение или `/allow <id> [имя]` |
| `/deny` | (владелец) убрать человека из списка |
| `/who` | показать список доступа |
| `⚙ пульт` (кнопка клавиатуры) | команды stream-сессии (панель VSCode / hub-launched): 🧮 контекст, 🌐 remote, 🧭 браузер, ⏳ лимит, 🗜 compact, ⏹ прервать (они же `/context` `/rc` `/browser` `/limits` `/compact` `/interrupt`) |
| `🧭 браузер` · `/browser` · `@browser` в тексте | подключить Chrome (claude-in-chrome MCP) к stream-сессии удалённо; `@browser …текст…` подключает и сразу отдаёт задачу |

Аппрувы приходят кнопками **только на реальные действия** (Bash/Write/…); ответы ассистента
(`reply`) авто-разрешены. Доступ — у `HUB_OWNER_ID` (в любом чате) и у людей из списка `~/.claude/channels/hub/access.json`
(только в групповых чатах; список ведётся командами `/allow` и `/deny`). См. «Бот в группе».

## Активная сессия — своя в каждом чате

Обычный текст уходит в активную сессию **того чата**, где он написан. Переключение в личке
не трогает группу и наоборот. Список живых сессий при этом общий: все чаты видят все сессии,
различается только отметка «активна».

На кнопках видно проект: `teamly · Ревью-PRs` — базовое имя каталога сессии и её название.

Если в чате активной сессии ещё нет, бот не теряет написанное: текст придерживается, а в ответ
приходит список сессий кнопками. Тап отправляет придержанное в выбранную сессию. Придержанное
живёт 10 минут; новое сообщение до выбора заменяет предыдущее.

Указатель очищается, когда сессия отключается, и никуда не перескакивает сам — иначе следующее
сообщение ушло бы в случайную сессию. Ответ на сообщение бота по-прежнему адресует сессию
напрямую, минуя указатель.

## Установка

### Требования

- **Node.js ≥ 22.** `tg-hub` тянет нативную зависимость `node-pty` — обычно ставится
  из prebuilt-бинаря; если для твоей версии Node его нет, понадобится тулчейн сборки
  (на Windows — «Desktop development with C++» из Visual Studio Build Tools + Python 3;
  на Linux/macOS — `build-essential`/Xcode CLT).
- **Claude Code CLI** (`claude` ≥ 2.1.80; проверено на 2.1.167) с выполненным входом
  в аккаунт **Pro/Max или Console** и доступом к **channels** (research preview,
  первопартийный провайдер). Проверка: `claude --version`.
- **Telegram-бот** от [@BotFather](https://t.me/BotFather) (получишь токен) и **твой
  Telegram user id** (узнать у [@userinfobot](https://t.me/userinfobot)).
- **git**.

### Шаги

1. **Клонировать и поставить зависимости:**
   ```bash
   git clone https://github.com/vassav/claude-tg-hub.git
   cd claude-tg-hub/tg-hub
   npm install
   ```

2. **Создать `.env` в корне репозитория** (он в `.gitignore` — токен сюда, не в код):
   ```dotenv
   HUB_BOT_TOKEN=<токен от BotFather>
   HUB_OWNER_ID=<твой Telegram user id>     # управляет ботом (в любом чате)
   HUB_PORT=8799                            # локальный TCP-порт IPC (любой свободный)
   HUB_TOKEN=<любой локальный секрет>        # общий секрет hub↔shim
   # HUB_CHAT_ID=-1001234567890             # опц.: вести бота в этой группе вместо лички (см. «Бот в группе»)
   # CLAUDE_BIN=C:\path\to\claude.exe       # см. шаг 3
   ```
   Второй бот на той же машине — см. [«Несколько ботов на одной машине»](#несколько-ботов-на-одной-машине).

3. **Указать путь к `claude` (если он не дефолтный).** [`session.mjs`](tg-hub/session.mjs)
   по умолчанию ищет `claude.exe` по моему пути установки. На своей машине задай
   переменную `CLAUDE_BIN` (в `.env` или в окружении) на свой бинарь:
   - Windows: `where.exe claude` → возьми путь к `…\bin\claude.exe`;
   - Linux/macOS: `which claude`.

4. **Поправить рабочий каталог сессий.** Сейчас путь захардкожен под мою машину —
   замени `TMP` в [`hub.mjs`](tg-hub/hub.mjs#L28) и [`launch.mjs`](tg-hub/launch.mjs#L20)
   на свою папку (например, `%LOCALAPPDATA%\Temp\hubsessions` или `/tmp/hubsessions`).
   *(Это временные cwd для тестовых сессий `launch.mjs`; для реальной работы создавай
   сессии в нужных проектах через `/new <путь>` или `/projects`.)*

5. **Запуск** (два терминала из `tg-hub`):
   ```bash
   npm run hub       # терминал 1 — демон-бот (один поллер Telegram + IPC + реестр)
   npm run launch    # терминал 2 — опционально: поднять тестовые сессии sess-A/sess-B
   ```
   При первом запуске сессии PTY сами подтверждают стартовые промпты Claude
   (доверие к папке, предупреждение dev-channels) — нажатий не требуется.

6. **Проверка.** В Telegram из аккаунта владельца: `/start`, затем `/sessions` —
   переключайся между сессиями, пиши в активную, подтверждай действия кнопками.
   Реестр сессий сохраняется в `~/.claude/channels/hub/registry.json`, поэтому
   при рестарте демона живые сессии **переподцепляются**, а завершённые предлагаются
   как ⏸ resume (с полной историей).

### Несколько ботов на одной машине

Каждый бот — свой хаб со своим файлом настроек. Файл в том же формате, что `.env`, и
передаётся параметром:
```bash
node hub.mjs --config D:/bots/work.env
```
Значения из него перекрывают переменные окружения, так что хаб можно запускать откуда
угодно, даже из сессии другого хаба. Без `--config` берётся `.env` из корня репозитория.

У второго хаба должны быть свои бот-токен, `HUB_PORT` и папка состояния:
```dotenv
HUB_BOT_TOKEN=<токен второго бота>
HUB_OWNER_ID=<твой user id>
HUB_PORT=8801
HUB_TOKEN=<секрет>
HUB_STATE_DIR=work-state    # registry.json, access.json, hub.json; относительный путь — от папки файла
HUB_PROJECTS=D:/Work;E:/Clients/Acme   # опц.: папки, в которых боту можно работать
```

`HUB_PROJECTS` — одна или несколько папок через `;` (на Linux/macOS — через `:`). Бот
работает только с проектами внутри них, вложенность любая:
- в `/projects` видны только они (папка проекта определяется по `cwd` из истории разговора);
- `/new`, resume, ➕ и IPC-`start` в другую папку отказывают — `⛔ … outside this bot's projects`;
- чужая сессия (плагин с `HUB_JOIN=1`, панель VSCode) из другой папки не подключается:
  хаб пишет в лог `refused … outside HUB_PROJECTS` и молча её игнорирует.

Без `HUB_PROJECTS` боту доступны все проекты пользователя. Это ограничение того, что бот
делает из Telegram; запущенная сессия — обычный `claude` с твоими правами, и путь за
пределами папки в чате модели он не запрещает.
По умолчанию `HUB_STATE_DIR` — `~/.claude/channels/hub`. Если два хаба указывают на одну
папку или на один порт, второй сразу выходит с ошибкой и ничего не трогает.

Сессии, которые хаб запускает сам, знают свой хаб. Сессии с плагином (`HUB_JOIN=1`) и
панель VSCode ищут хаб по `hub.json` в `~/.claude/channels/hub` — чтобы они пошли ко
второму, задай им `HUB_STATE_DIR` той же папкой (абсолютным путём).

> Сессии хаба переживают рестарт демона: каждая привязана к UUID разговора Claude
> (через `--session-id`), хаб хранит `uuid+cwd` и проверяет живость процесса по PID,
> чтобы не запустить один разговор дважды.

## Как выглядят ответы

Ответы сессий уходят Rich Messages (Bot API 10.1): Markdown модели отдаётся Telegram как
есть, и клиент рисует его сам — таблицы с границами и выравниванием, заголовки, списки,
блоки кода с подсветкой и меткой языка, цитаты. Конвертации на нашей стороне нет.

Побочный эффект: лимит сообщения 32768 символов вместо 4096, поэтому длинные ответы почти
перестали резаться на куски (а таблица больше не рвётся посередине).

Тем же путём уходят и уведомления тула `notify` — это такой же Markdown от модели.

Если Telegram отказал — например, `TELEGRAM_API_ROOT` указывает на self-hosted Bot API
server старее 10.1, или ответ упёрся в лимит (500 блоков, 20 колонок, 16 уровней
вложенности) — сообщение уходит прежним путём, через Markdown→HTML. Ничего не теряется,
но таблицы в этом режиме рисовать нечем, поэтому причина отказа пишется в лог демона
строкой `[rich] rejected: …` — иначе подмену не отличить от обычного ответа.

## Кто из сессий сейчас работает

`/sessions` показывает не только список, но и состояние каждой сессии:

| Отметка | Значение |
|---|---|
| `⚡ 1 м 20 с · 3.4k` | идёт ход: сколько уже длится и сколько токенов выдано |
| `🔐 ждёт аппрув` | сессия упёрлась в подтверждение инструмента и ждёт человека |
| `●` / `○` | активная в этом чате / просто живая |

Токены знают только stream-сессии (панель VSCode / `HUB_STREAM=1`), у channels-сессий
движок их не отдаёт — тогда показывается одно время. Ход, о котором больше десяти минут
нет ни одного сигнала, считается законченным: сессия могла умереть молча.

Границы хода stream-сессия сообщает явно: мост шлёт хабу `turn start` на user-сообщении
движка (поэтому ход, начатый прямо в панели, тоже виден) и `turn end` на его `result`.
Ответом отметку снимать нельзя — модель говорит и в середине хода, а сразу после ответа
движок присылает ещё и счётчик токенов. У channels-сессий никакого сигнала конца нет,
там отметка гаснет по ответу.

Список — снимок на момент запроса, поэтому под ним есть кнопка **🔄 обновить**: она
перерисовывает то же сообщение на месте.

## Бот в группе

Два независимых сценария — их можно использовать порознь.

**1. Несколько человек работают с ботом в группе (список доступа).** `.env` не меняется.

1. Добавь бота в группу и сделай его **администратором** — иначе Telegram (privacy mode)
   отдаст ему только команды, реплаи на его сообщения и упоминания.
2. Пусть человек что-нибудь напишет в группе. Ответь на его сообщение командой `/allow` —
   бот возьмёт user_id из цитаты. Или `/allow <user_id> [имя]`, если id уже известен
   (человек может узнать свой через `/id` в группе).
3. Всё: его сообщения в **любом** групповом чате, где есть бот, теперь обрабатываются.
   Рестарт хаба не нужен, список читается горячо.

`/who` — посмотреть список, `/deny` — убрать. Менять список может только владелец.

Что уходит в группу: всё, что нужно, чтобы продолжить работу оттуда, — ответы сессии
(цитатой на сообщение автора), карточки аппрувов инструментов (✅ Allow / ❌ Deny) и
карточки AskUserQuestion. Всё это приходит в чат, из которого сессию вели последней;
если отправить туда не вышло (бота убрали из группы, группа сменила id), карточка уходит
владельцу в личку, чтобы сессия не повисла. У сессий на `channels` (режим по умолчанию, пока
`HUB_STREAM` не задан) AskUserQuestion приходит не карточкой с вариантами, а дайджестом
вопроса с кнопками Allow/Deny.

Значит, **нажать ✅ на `Bash(rm -rf …)` может любой человек из списка, который есть в этой
группе**, — и кнопки «больше не спрашивать» тоже: правило записывается в настройки проекта
насовсем. Участники группы не из списка карточки видят, но нажатия бот игнорирует. В личке
владельца остаются только уведомления хаба.

Личка с ботом остаётся только у владельца: человек из списка, написавший боту в ЛС,
доступа не получит.

⚠️ Человек из списка может позвать бота в любую свою группу. Управлять ботом посторонние
там не смогут, но увидят ответы — а в них содержимое твоих проектов. Кроме того, `/rc` в
такой группе отдаёт ссылку на продолжение сессии claude.ai в чат, откуда её вызвали, а
`/browser` подключает к сессии твой залогиненный Chrome — обе команды доступны всем из
списка. Добавляй в список только тех, кому доверяешь эти данные.

**2. Вести весь вывод бота в группе вместо лички.** Задать `HUB_CHAT_ID=-100…` и
перезапустить хаб — тогда туда уходят уведомления и карточки сессий, у которых ещё нет
чата (запущенных из панели или IPC-`start`). Сценарий для «личного» чата, где ты один; в
общей группе не используй — такие аппрувы станут доступны всем из списка.
Если `HUB_CHAT_ID` у тебя уже указывал на общую группу: раньше писать боту и получать
ответы мог любой участник этой группы, теперь такие участники игнорируются, пока владелец
не добавит их через `/allow`.

## Сессии, запущенные тобой (не хабом)

Любую свою сессию можно присоединить к работающему хабу:
```bash
HUB_JOIN=1 claude --dangerously-load-development-channels plugin:hub@tg-hub-dev
```
(плагин устанавливается из `spike/hub-marketplace`; на личном Pro/Max managed-allowlist для
запуска без dev-флага не действует — см. [спеку](docs/specs/2026-06-06-channels-validated-and-hub-design.md)).
shim сам найдёт хаб и зарегистрирует сессию; `HUB_JOIN=1` — явный opt-in, чтобы обычные
сессии не подключались.

Плагин даёт сессии MCP-тулы `reply`/`set_title` (для подключённых к хабу) **и `notify`** —
отправить уведомление в Telegram напрямую: `notify(text)` без `chat_id`. `notify` работает
**даже без присоединения** к хабу — достаточно загрузить плагин (без `HUB_JOIN`); удобно
«пингнуть» себя, когда долгая задача в обычной сессии завершилась. Доставляет через
единственного бота хаба, поэтому бот-токен самой сессии не нужен.

**`send_file`** — отправить в чат локальный файл: `send_file(path, caption?, chat_id?, as?)`.
По умолчанию `.png/.jpg/.gif/.webp` уходят картинкой, остальное (PDF, лог, …) — документом;
`as:"document"` форсирует документ (картинка без пережатия), `as:"photo"` — наоборот. Путь —
на машине сессии (абсолютный или относительный к её рабочей папке); байты не гоняются по сети —
хаб читает файл с диска. Как и `notify`, работает даже без присоединения к хабу.

## External IPC (создание/инжект из своей тулзы)

Локальный процесс-консьюмер (НЕ человек в Telegram) может программно управлять хабом по тому же
TCP-IPC: подключиться к `127.0.0.1:<HUB_PORT>`, прочитать `port`/`token` из
`~/.claude/channels/hub/hub.json` (у хаба с `HUB_STATE_DIR` — из его папки; или взять из env
`HUB_PORT`/`HUB_TOKEN`) и слать
**newline-terminated JSON**. Неверный `token` → сокет закрывается.

**`start`** — создать новую managed-сессию (durable/resumable, процессом владеет демон) или
возобновить известную:
```json
{"t":"start","token":"<HUB_TOKEN>","cwd":"d:/path/to/project",
 "resume":"<uuid|опц.>","content":"первый ход (опц.)","meta":{"chat_id":"<опц.>"},
 "extraMcpServers":{"<name>":{"command":"node","args":["mcp.mjs"]}},"extraAllowedTools":["mcp__name__tool"]}
```
→ `{"ok":true,"id":"<uuid>"}` (или `{"ok":false,"error":…}`). `content` инжектится первым
ходом, как только сессия зарегистрируется. `resume` берёт `cwd` из реестра, если не передан.
Доп. MCP-серверы консьюмера видны сессии; их тулы проходят обычный аппрув кнопками (если не
перечислены в `extraAllowedTools`).

**`inject`** — отправить сообщение в **уже живую** сессию (как обычное входящее):
```json
{"t":"inject","token":"<HUB_TOKEN>","target":"<label|id>","content":"привет","meta":{"chat_id":"<опц.>"}}
```
→ `{"ok":true}` или `{"ok":false,"error":"session not connected"}`.

**`notify`** — разовое уведомление в «домашний» чат, без сессии (это же шлёт тул `notify`
плагина):
```json
{"t":"notify","token":"<HUB_TOKEN>","text":"готово ✅","chat_id":"<опц.>"}
```
→ `{"ok":true}`.

**`send_file`** — локальный файл в чат, без сессии (это же шлёт тул `send_file` плагина). Хаб
читает `path` с диска (хаб и клиент на одной машине), фото/документ выбирается по расширению
или полем `as`:
```json
{"t":"send_file","token":"<HUB_TOKEN>","path":"C:\\tmp\\shot.png","caption":"<опц.>","chat_id":"<опц.>","as":"auto|photo|document"}
```
→ `{"ok":true,"method":"sendPhoto"}` или `{"ok":false,"error":"file not found: …"}`.

Нюансы:
- После `start` сессия становится «живой» через ~1–2с (регистрация). Слишком ранний `inject`
  вернёт `session not connected` — либо ретрай до `{ok:true}`, либо передавай первый ход прямо
  в `start.content`.
- `meta.chat_id` по умолчанию = «домашний» чат (`HUB_CHAT_ID` или личка владельца) — туда уйдут
  ответы и аппрувы сессии.
- Стоп-IPC намеренно нет: завершай сессию из Telegram (`/stop`/🛑).

## VSCode-панель (мост через интерпозер)

Сессию **панели VSCode** тоже можно подключить к хабу — отдельным путём, т.к. в SDK-режиме
панели channel-инъекция не запускает ход модели. Stdio-интерпозер садится между расширением и
`claude.exe` (через настройку `claudeCode.claudeProcessWrapper`), прозрачно форвардит stream-json
и работает «shim'ом панели»: ответы зеркалит в Telegram, сообщения из TG инжектит как user-turn'ы,
аппрувы шлёт кнопками (control-протокол `can_use_tool` — на свежих версиях claude он, в отличие от
channels, не авто-аппрувится). Пока сессия привязана к Telegram, запрос аппрува перехватывается и
в панель не отдаётся — её диалог не зависает.

Код — в [`tg-hub/panel/`](tg-hub/panel/) (`interposer.mjs` + `panel-wrapper.cs`). Сборка
wrapper'а, настройка и проверенный stream-json — в спеке
[`docs/specs/2026-06-11-vscode-panel-bridge.md`](docs/specs/2026-06-11-vscode-panel-bridge.md).

## Как устроены channels (кратко)

`channel` = MCP-сервер, который в `initialize` объявляет
`capabilities.experimental: { "claude/channel": {}, "claude/channel/permission": {} }`.
Движок пушит ему входящие (`notifications/claude/channel`) и запросы аппрува
(`…/permission_request` → `…/permission`); наружу ассистент отвечает через MCP-tool `reply`.
Активируется флагом `--channels <plugin:name@marketplace | server:name>` (для кастома —
`--dangerously-load-development-channels`).

Полный разбор контракта, gate и проверенные в бинаре факты:
- [`docs/specs/2026-06-06-channels-validated-and-hub-design.md`](docs/specs/2026-06-06-channels-validated-and-hub-design.md)
- официальные доки: [channels](https://code.claude.com/docs/en/channels.md),
  [channels-reference](https://code.claude.com/docs/en/channels-reference.md)

## Ограничения

- `channels` — research-preview: синтаксис/контракт могут меняться между версиями.
- Кастомный канал активируется dev-флагом; managed-allowlist (`allowedChannelPlugins`) — фича
  Team/Enterprise, на личном Pro/Max не применяется.
- Голый `claude` без `--channels` подцепить задним числом нельзя (анонимный stdio).
- VSCode-панель покрыта отдельным путём (stdio-интерпозер через `claudeProcessWrapper`,
  см. [спек](docs/specs/2026-06-11-vscode-panel-bridge.md)); пути wrapper'а захардкожены под Windows.
- Код на `.mjs` (zero-build), один администратор-бот (`HUB_OWNER_ID`; опц. общая группа через
  `HUB_CHAT_ID`); формальных тестов нет (есть smoke- и e2e-проверки). TS-пакет и
  кроссплатформенные пути — в планах.
